Do not deploy only dist/ for the real service A static dist/ upload cannot provide Admin, contact storage, accounts, inventory, orders, payment, SMS, or live CMS content. The full Node process is required.

Data that must survive every code update

  • khyeast.db plus its WAL state — revisioned Admin content, products, stock, customers, addresses, orders, sessions, OTP records, messages, comments, payment history, SMS and settings.
  • uploads/ — images, videos, and responsive image variants.
  • ADMIN_SECRET and the rest of the production environment — never lose the stable secret.

This guide keeps mutable state in /var/lib/khyeast, outside the Git checkout. Git contains only immutable code/defaults, so an Admin save cannot conflict with git pull. On a demonstrably fresh persistent tree, the application creates the complete final schema and initializes all nine editorial sections plus operational defaults directly from immutable JavaScript defaults. It has no JSON importer, seed file, ALTER, backfill, or automatic schema-upgrade path. An established missing, incompatible, or corrupt database is never silently changed or reseeded.

What this guide deliberately uses

Ubuntu/Debian VPS

Commands target Ubuntu 24.04 LTS or a current Debian-based equivalent with sudo access.

One Node process

Start with one reliable process. SQLite is local and the expected load does not require a cluster.

systemd

Automatic start, restart, shutdown signals, resource ownership, and journal logs.

Nginx

Public ports, TLS, canonical redirects, forwarding headers, and upload limits.

Prepare accounts, domain, and server

Gather everything first. Most failed launches are missing-access or DNS problems, not application problems.

Recommended server size

ResourceMinimumRecommended starting point

Disk20 GB SSD40+ GB SSD, sized for uploads and backup retention
OS64-bit LinuxUbuntu 24.04 LTS
NetworkPorts 22, 80, 443Static public IP and provider firewall
Upload staging and memory The application preserves the 200 MB file limit but streams each multipart body to private UPLOAD_DIR/.incoming storage instead of retaining it as a JavaScript Buffer. One upload per Node process is admitted at a time; videos publish by atomic rename and Sharp reads images from that staged path. The response is sent only after staging cleanup and slot release, so the next sequential gallery upload is not mistaken for a concurrent request. Image decoding still needs memory bounded by the pixel limit, so 4 GB remains the safer baseline. Keep at least one upload plus generated variants free on the upload filesystem.

  • A Linux server with a static public IPv4 address.
  • A sudo-capable SSH account using an SSH key.
  • Control of the domain's DNS records.
  • Read access to m-ali-98/Khyeastwebsite (deploy key if private).
  • Production Admin username and a strong password.
  • ZarinPal and sms.ir credentials, if those features will be enabled.
  • An off-server destination for encrypted backups.

Install Node.js 22 or newer

The project requires Node.js 22+. Use a supported LTS release. The commands below use NodeSource for Node 22; if your organization has an approved package source, use that instead.

Install from NodeSource

Download the setup script, inspect it, then run it. Do not pipe an unseen remote script directly into a privileged shell.

cd /tmp

less nodesource_setup.sh

command -v npm
Expectednode --version must report v22.x or a newer supported release. The systemd examples assume Node is at /usr/bin/node; use the path printed by command -v node if different.

Why not use nvm for the system service?

nvm is excellent for interactive development, but a systemd service does not load your shell profile. A system-wide, pinned Node installation produces a simpler and more predictable production service. If you must use nvm, put the absolute Node binary path in ExecStart and document the version-owner relationship.

Create users, directories, and persistent storage

A human deployment user owns the code. A locked service account runs Node. Only the mutable data directories are writable by the application.

Create the service account and directories

# Locked system account; no interactive shell.
sudo adduser --system --group --home /var/lib/khyeast khyeast

# Versioned code. The human deployment user owns releases.
sudo install -d -m 0750 -o "$USER" -g khyeast /srv/khyeast
sudo install -d -m 0750 -o "$USER" -g khyeast /srv/khyeast/releases

sudo install -d -m 0750 -o khyeast -g khyeast /var/lib/khyeast/data
sudo install -d -m 0750 -o khyeast -g khyeast /var/lib/khyeast/uploads

sudo install -d -m 0700 -o root -g root /etc/khyeast

Initialize the complete store once on fresh storage

No seed JSON or import source is shipped or accepted. Before the first service start, confirm that the configured database does not exist and that the persistent data and upload trees contain no files.   -mindepth 1 ! -type d -print

Protect and preserve ADMIN_SECRET Every process must use the same stable value. Treat it as backup-critical. Rotating it invalidates Admin sessions and intentionally starts fresh rate-limit buckets; it also invalidates outstanding OTP hashes. Do not rotate it casually during an update.

Optional settings

  • TRUSTED_HOSTS: valid aliases in addition to PUBLIC_ORIGIN.
  • TRUST_PROXY: keep the safe default for same-host Nginx. Never set true unless direct access to Node is impossible and the proxy topology is fully controlled.
  • RATE_LIMITS_ENABLED and RL_MAX_*: initial overrides only. Saved Admin settings later become authoritative.
  • SEO_ORIGIN: optional build-only origin; normally PUBLIC_ORIGIN is enough.
  • PENDING_ORDER_TTL_MS: default is approximately 30 minutes. Do not change without understanding inventory behavior.

What does not belong in this file

ZarinPal and sms.ir settings are managed inside Admin and stored in the application database. Do not duplicate them in Git. Do not commit .env, environment files, database copies, private keys, or backup archives.

Chapter 8

Run the application with systemd

systemd starts the application after boot, restarts it on failure, passes secrets without exposing them in the unit, and sends SIGTERM for a clean SQLite shutdown.

Create the service unit

sudo tee /etc/systemd/system/khyeast.service >/dev/null <<'UNIT'
[Unit]
Description=Khuzestan Yeast website and API
Wants=network-online.target
After=network-online.target

[Service]
Type=simple
User=khyeast
Group=khyeast
WorkingDirectory=/srv/khyeast/current
EnvironmentFile=/etc/khyeast/khyeast.env
ExecStart=/usr/bin/node server/index.js
Restart=on-failure
RestartSec=5s
TimeoutStopSec=120s
KillSignal=SIGTERM
UMask=0027

NoNewPrivileges=true
PrivateTmp=true
ProtectSystem=full
ProtectHome=true
ProtectKernelTunables=true
ProtectKernelModules=true
ProtectControlGroups=true
ReadWritePaths=/var/lib/khyeast

[Install]
WantedBy=multi-user.target
UNIT

If command -v node returned a different path, change ExecStart. The application stops accepting new connections on SIGTERM, drains active HTTP requests for up to 90 seconds, and only then closes SQLite. Keep TimeoutStopSec above that bound so systemd does not kill an in-flight ZarinPal verification first.

Start and enable the service

sudo systemctl daemon-reload
sudo systemctl enable --now khyeast
sudo systemctl status khyeast --no-pager
sudo journalctl -u khyeast -n 100 --no-pager

curl -fsS http://127.0.0.1:8787/api/health

The 210 MB allowance is scoped to the exact authenticated upload endpoint. proxy_request_buffering off streams that body to the application's private disk stage instead of creating a second complete Nginx request-body copy. Every other route remains under the 8 MB JSON/application ceiling, so a large request cannot consume proxy resources on login, callbacks, contact, or ordinary API routes.

Certificate pathsCertbot uses a directory named after the certificate's primary name. Confirm with sudo certbot certificates and adjust the paths if your certificate directory differs.

Why the proxy headers are exact

  • Host preserves the real public hostname for canonical and trust checks.
  • X-Forwarded-For carries the visitor chain. Express accepts it only from trusted proxy peers.
  • X-Forwarded-Proto https lets Node issue the production __Host-ky_admin Secure cookie and HSTS.
  • The port-80 virtual host redirects and never proxies. This prevents a real HTTP request from being mistaken for HTTPS if a protocol header is absent.
  • The exact ZarinPal callback location intercepts proxy-unavailable errors and the application's explicit retryable verification 503. Its page refreshes the original URL; it does not claim success, alter the authority query, or mask an application-generated 4xx/500 response.

The private .incoming directory is different: it contains only an upload that has not yet been accepted. Why active and stopped-service snapshots are conservative

  1. Measure the live payload and require room for staging, an uncompressed archive, and a 1 GiB post-estimate reserve before copying.
  2. Copy live uploads into a fresh stage, excluding .quarantine and transient .incoming bodies.
  3. Validate the live SQLite application id, schema version, content metadata and all nine section types; record its monotonic revision.
  4. If khyeast.service is active, run SQLite .backup. If systemd confirms it is inactive, copy the stable main file; if WAL survived an unclean stop, copy the main/WAL/SHM set and consolidate only that writable staged copy.

Split Restic upload from trusted maintenance

Choose a Restic-compatible backend with a documented append-only mode (for example, rest-server --append-only or an equivalent provider policy). The VPS credential may read what Restic needs for deduplication and append new repository objects, but it must not overwrite or delete established packs, indexes, snapshots, keys, or repository history. A backup creates a repository lock and removes it afterwards. Although upstream Restic exposes the global --no-lock option in backup --help, released Restic and current upstream do not honor it for backup (see upstream issue #1544); adding that flag would provide false assurance while the lock is still created. The endpoint must instead permit deletion only for ephemeral locks/* objects while denying history deletion, as Rest Server's append-only mode does. If a provider cannot scope that exception, do not point Restic directly at its no-delete credential; put a compatible append-only REST/rclone boundary in front of it. Lock-taking check, forget, prune, and unlock remain exclusive to the full-access maintenance host. Validate the exact restricted credential in a disposable repository before production. RESTIC_APPEND_ONLY=true is only an operator assertion and startup guard; provider-side authorization is the real control.

SIGTERM first closes the Node listener and drains active requests for up to 90 seconds before SQLite closes. A callback already being verified can therefore finish. A callback arriving during the remaining restart gap receives the dedicated Nginx 503 page and automatically retries the same authority URL instead of inviting a second payment.

  • Admin login on the real HTTPS hostname works and Security reports the correct protocol and client IP.
  • Content reports X-Khyeast-Content-Status: persisted, not fallback.
  • Stock, recent orders and payment-attempt history are intact.
  • A safely repeatable settled callback URL still produces the settled result rather than a new attempt.
  • Application, Nginx, backup and quarantine-timer logs contain no new error.

Rollback

If smoke tests fail, inspect logs, then atomically return the symlink to the previously printed directory:

Code rollback is not a data rollbackThis application never changes an existing schema; an incompatible release fails startup instead. A release that did start may still have changed orders, payments and other mutable state. Stop the service, assess activity since the snapshot, and restore one coherent whole-database backup only when the reconciliation plan is explicit.

When a restart gap is still unacceptable

A graceful single process protects requests already in flight but cannot accept a new connection while the next process starts. True continuous service needs two ports or hosts: start and health-check the new release, switch the Nginx upstream, then drain the old release. Use that blue/green pattern only when both releases declare the same exact database schema contract and shared SQLite write load has been tested. The static callback retry page remains useful defense in depth.

Rules for every update Record old and new commit IDs; require the same exact database schema contract; verify the validated local snapshot and append-only offsite replication; build outside the live release; never replace /var/lib/khyeast; cut over atomically; smoke-test payment and Admin; then monitor closely.

Chapter 16

cPanel / Apache / Passenger appendix

Use this chapter instead of systemd/Nginx when the Linux host is managed by cPanel's “Setup Node.js App” and Passenger. The same application, state, HTTPS, and proxy rules still apply.

Application setup

  1. Select Node.js 22 or newer and production mode.
  2. Place the repository outside public_html.
  3. Set the application root to the repository and startup file to server/index.js.
  4. Do not manually set PORT unless the host explicitly requires it; Passenger normally injects the listening endpoint.
  5. Add the required environment variables from Chapter 7 through cPanel's environment UI.
  6. Use persistent writable paths for DATA_DIR, DB_FILE, and UPLOAD_DIR. Ensure every Passenger worker sees the same local files.
  7. Build and test a separate release directory before switching Passenger's application root; do not run npm ci beneath live workers.
  8. Restart through cPanel's application control. Use Passenger's restart mechanism only if your host documents it.
  9. Use Cron Jobs to run npm run uploads:purge-quarantine daily as the application user, with the production UPLOAD_DIR.
  10. Use a hosting backup job that invokes SQLite .backup, validates all nine CMS sections and a stable revision, and excludes UPLOAD_DIR/.quarantine plus UPLOAD_DIR/.incoming; a raw copy of the live WAL database is not sufficient.

Apache proxy contract

  • Prefer X-Forwarded-Proto: https on the HTTPS virtual host.
  • Preserve the public Host.
  • Forward the real client chain in X-Forwarded-For.
  • Port 80 must redirect to HTTPS before Passenger. If port 80 must be proxied, it must explicitly send X-Forwarded-Proto: http; it must never omit the protocol header.
  • Keep the Passenger/internal Node endpoint inaccessible to public clients.
  • Ask the host to provide an equivalent no-store 503 retry page for the exact ZarinPal callback path during Passenger restarts; it must preserve the query string and must not report success.
Guarded fallback is not a replacement for a correct proxy If a trusted cPanel/Apache proxy omits X-Forwarded-Proto, production can infer HTTPS only when PUBLIC_ORIGIN is HTTPS, the real Host matches PUBLIC_ORIGIN/TRUSTED_HOSTS, and the socket peer is trusted. A port-80 redirect is still mandatory.

Rate-limit counters and reservations are stored in SQLite, so ceilings do not multiply by worker count. SQLite still requires one local persistent data path and short writes. Monitor SQLITE_BUSY and avoid an excessive Passenger worker count. Every worker must receive the same ADMIN_SECRET.

Chapter 17

Static-only deployment limits

A static host can publish dist/ as a limited read-only fallback, but it is not a complete deployment of this product.

What static hosting can provide

  • Built public pages and assets.
  • Generated route HTML, sitemap, robots, canonical metadata, and static 404 behavior where the host honors the generated rules.
  • Only the content present at build time.

What static hosting cannot provide

  • Admin login or content publication.
  • Contact-message storage.
  • Customer accounts, OTP, addresses, or sessions.
  • Cart checkout, live inventory, orders, or comments.
  • ZarinPal payment creation, callback verification, inquiry, reverse, or refund.
  • sms.ir delivery.
  • Uploads or unused-file cleanup.
  • Runtime SEO based on current CMS/database content.
DecisionIf the site will sell products or use Admin, deploy the Node application. Do not point the domain at npm run preview; Vite preview is not the production API server.
