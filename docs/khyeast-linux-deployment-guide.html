Chapter 1

Understand the production architecture

This is not a static brochure. The same Node.js application serves the built React site, route-aware SEO HTML, APIs, Admin, uploads, customer accounts, orders, inventory, payment callbacks, and SMS workflows.

The four production layers

LayerResponsibilityRecommended component
DNSMaps the public domain to the serverYour DNS provider
EdgeTLS, port 80 redirect, request forwarding, upload limitNginx + Let's Encrypt
ApplicationWebsite, API, Admin, callbacks, runtime SEONode.js managed by systemd
StateContent, SQLite, uploads, settings, payment historyLocal persistent SSD + backups
Do not deploy only dist/ for the real service A static dist/ upload cannot provide Admin, contact storage, accounts, inventory, orders, payment, SMS, or live CMS content. The full Node process is required.

Data that must survive every code update

  • content.json — Admin-edited page content and translation overrides.
  • khyeast.db plus its WAL state — products, stock, customers, addresses, orders, sessions, OTP records, messages, comments, payment history, SMS and rate-limit settings.
  • uploads/ — images, videos, and responsive image variants.
  • ADMIN_SECRET and the rest of the production environment — never lose the stable secret.

This guide keeps mutable state in /var/lib/khyeast, outside the Git checkout. That separation makes updates safer and prevents a mistaken checkout or cleanup from destroying production data.

What this guide deliberately uses

Ubuntu/Debian VPS

Commands target Ubuntu 24.04 LTS or a current Debian-based equivalent with sudo access.

One Node process

Start with one reliable process. SQLite is local and the expected load does not require a cluster.

systemd

Automatic start, restart, shutdown signals, resource ownership, and journal logs.

Nginx

Public ports, TLS, canonical redirects, forwarding headers, and upload limits.

Chapter 2

Prepare accounts, domain, and server

Gather everything first. Most failed launches are missing-access or DNS problems, not application problems.

Recommended server size

ResourceMinimumRecommended starting point
CPU1 vCPU2 vCPU
Memory2 GB4 GB, especially when building and optimizing uploads
Disk20 GB SSD40+ GB SSD, sized for uploads and backup retention
OS64-bit LinuxUbuntu 24.04 LTS
NetworkPorts 22, 80, 443Static public IP and provider firewall
Upload memory The application allows a file up to 200 MB and validates uploads in memory. Four gigabytes of RAM is the safer baseline if administrators upload large videos. If large videos are unnecessary, enforce a smaller Nginx limit operationally.

Access checklist

  • A Linux server with a static public IPv4 address.
  • A sudo-capable SSH account using an SSH key.
  • Control of the domain's DNS records.
  • Read access to m-ali-98/Khyeastwebsite (deploy key if private).
  • Production Admin username and a strong password.
  • ZarinPal and sms.ir credentials, if those features will be enabled.
  • An off-server destination for encrypted backups.

Choose one canonical domain

Examples in this guide use example.com as canonical and redirect www.example.com to it. Replace both everywhere. The application's PUBLIC_ORIGIN must be the exact final HTTPS origin, with no trailing slash:

PUBLIC_ORIGIN=https://example.com

Chapter 3

Secure the base Linux system

Work from a sudo user. Never run the application as root, and never expose the Node port directly to the internet.

Update the operating system

sudo apt update
sudo apt full-upgrade -y
sudo apt install -y \
  git curl ca-certificates nginx certbot python3-certbot-nginx \
  sqlite3 build-essential python3 ufw

sudo timedatectl set-timezone UTC
sudo timedatectl set-ntp true

# Reboot if the kernel or core libraries were upgraded.
sudo reboot

Reconnect after the reboot and confirm:

uname -a
timedatectl
systemctl --failed

Use a dedicated human deployment account

If your cloud image already supplied a non-root sudo user, keep it. Otherwise, from the provider console or an existing root session:

adduser deploy
usermod -aG sudo deploy
install -d -m 700 -o deploy -g deploy /home/deploy/.ssh
# Add the deploy user's public key to:
nano /home/deploy/.ssh/authorized_keys
chown deploy:deploy /home/deploy/.ssh/authorized_keys
chmod 600 /home/deploy/.ssh/authorized_keys

Harden SSH—without locking yourself out

Keep a second SSH session openProve key login works in a new terminal before disabling password or root login. Keep your provider's rescue console available.
sudo nano /etc/ssh/sshd_config.d/99-production-hardening.conf
PermitRootLogin no
PasswordAuthentication no
KbdInteractiveAuthentication no
PubkeyAuthentication yes
sudo sshd -t
sudo systemctl reload ssh
# Open a second terminal and test before closing the first.
ssh deploy@example.com

Enable the host firewall

sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow OpenSSH
sudo ufw allow 'Nginx Full'
sudo ufw enable
sudo ufw status verbose

Mirror the same rule at the cloud-provider firewall: allow 22 only from trusted administration IPs when practical, allow 80/443 publicly, and do not allow 8787.

Optional swap for small servers

If swapon --show is empty, a 2 GB swap file can keep a small VPS build from being killed. It does not replace enough RAM:

sudo fallocate -l 2G /swapfile
sudo chmod 600 /swapfile
sudo mkswap /swapfile
sudo swapon /swapfile
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
swapon --show
Chapter 4

Install Node.js 22 or newer

The project requires Node.js 22+. Use a supported LTS release. The commands below use NodeSource for Node 22; if your organization has an approved package source, use that instead.

Install from NodeSource

Download the setup script, inspect it, then run it. Do not pipe an unseen remote script directly into a privileged shell.

cd /tmp
curl -fsSLo nodesource_setup.sh https://deb.nodesource.com/setup_22.x
less nodesource_setup.sh
sudo -E bash nodesource_setup.sh
sudo apt install -y nodejs

Verify the actual runtime:

node --version
npm --version
command -v node
command -v npm
Expectednode --version must report v22.x or a newer supported release. The systemd examples assume Node is at /usr/bin/node; use the path printed by command -v node if different.

Why not use nvm for the system service?

nvm is excellent for interactive development, but a systemd service does not load your shell profile. A system-wide, pinned Node installation produces a simpler and more predictable production service. If you must use nvm, put the absolute Node binary path in ExecStart and document the version-owner relationship.

Chapter 5

Create users, directories, and persistent storage

A human deployment user owns the code. A locked service account runs Node. Only the mutable data directories are writable by the application.

Create the service account and directories

# Locked system account; no interactive shell.
sudo adduser --system --group --home /var/lib/khyeast khyeast

# Code location. The current human sudo user owns deployments.
sudo install -d -m 0750 -o "$USER" -g khyeast /srv/khyeast

# Persistent writable state.
sudo install -d -m 0750 -o khyeast -g khyeast /var/lib/khyeast/data
sudo install -d -m 0750 -o khyeast -g khyeast /var/lib/khyeast/uploads

# Root-only environment configuration.
sudo install -d -m 0700 -o root -g root /etc/khyeast

Why these locations?

PathOwnerPurpose
/srv/khyeast/appDeployment userGit checkout, dependencies, and built assets
/var/lib/khyeast/datakhyeastcontent.json and SQLite database
/var/lib/khyeast/uploadskhyeastUploaded images, videos, and image variants
/etc/khyeast/khyeast.envroot, mode 600Production secrets and runtime configuration
Use local persistent storage SQLite WAL should live on the server's local persistent filesystem, not an ephemeral container layer and not a generic NFS share. If you later scale across machines, move state to architecture designed for shared access rather than mounting one SQLite file over the network.

Chapter 7

Configure production secrets and environment

Production startup deliberately fails when required security values are missing, too short, or still equal to the published development defaults.

Generate strong values

# Example 48-character Admin password. Store it in a password manager.
openssl rand -hex 24

# Stable 64-character signing/HMAC secret.
openssl rand -hex 32

Create the environment file with sudoedit:

sudoedit /etc/khyeast/khyeast.env
NODE_ENV=production
PORT=8787

ADMIN_USER=choose-a-private-admin-name
ADMIN_PASS="PASTE-THE-48-CHARACTER-PASSWORD"
ADMIN_SECRET=PASTE-THE-64-CHARACTER-SECRET

PUBLIC_ORIGIN=https://example.com
TRUSTED_HOSTS="example.com,www.example.com"
TRUST_PROXY="loopback, linklocal, uniquelocal"

DATA_DIR=/var/lib/khyeast/data
UPLOAD_DIR=/var/lib/khyeast/uploads
DB_FILE=/var/lib/khyeast/data/khyeast.db

# Optional ownership tokens:
# GOOGLE_SITE_VERIFICATION=...
# BING_SITE_VERIFICATION=...
sudo chown root:root /etc/khyeast/khyeast.env
sudo chmod 600 /etc/khyeast/khyeast.env
sudo stat /etc/khyeast/khyeast.env

Required variables

VariableRuleWhy it matters
NODE_ENVExactly productionEnables secure production behavior and configuration refusal
ADMIN_USERPrivate, non-default usernameAdmin login identity
ADMIN_PASSAt least 12 characters; use much moreAdmin login credential
ADMIN_SECRETAt least 32 characters; stable across workers and restoresAdmin signing, OTP pepper, rate-limit HMAC separation
PUBLIC_ORIGINExact HTTPS origin, no path or trailing slashCallbacks, cookies, canonical URLs, sitemap, trusted-host fallback
Protect and preserve ADMIN_SECRET Every process must use the same stable value. Treat it as backup-critical. Rotating it invalidates Admin sessions and intentionally starts fresh rate-limit buckets; it also invalidates outstanding OTP hashes. Do not rotate it casually during an update.

Optional settings

  • TRUSTED_HOSTS: valid aliases in addition to PUBLIC_ORIGIN.
  • TRUST_PROXY: keep the safe default for same-host Nginx. Never set true unless direct access to Node is impossible and the proxy topology is fully controlled.
  • RATE_LIMITS_ENABLED and RL_MAX_*: initial overrides only. Saved Admin settings later become authoritative.
  • SEO_ORIGIN: optional build-only origin; normally PUBLIC_ORIGIN is enough.
  • PENDING_ORDER_TTL_MS: default is approximately 30 minutes. Do not change without understanding inventory behavior.

What does not belong in this file

ZarinPal and sms.ir settings are managed inside Admin and stored in the application database. Do not duplicate them in Git. Do not commit .env, environment files, database copies, private keys, or backup archives.

Chapter 8

Run the application with systemd

systemd starts the application after boot, restarts it on failure, passes secrets without exposing them in the unit, and sends SIGTERM for a clean SQLite shutdown.

Create the service unit

sudo tee /etc/systemd/system/khyeast.service >/dev/null <<'UNIT'
[Unit]
Description=Khuzestan Yeast website and API
Wants=network-online.target
After=network-online.target

[Service]
Type=simple
User=khyeast
Group=khyeast
WorkingDirectory=/srv/khyeast/app
EnvironmentFile=/etc/khyeast/khyeast.env
ExecStart=/usr/bin/node server/index.js
Restart=on-failure
RestartSec=5s
TimeoutStopSec=30s
KillSignal=SIGTERM
UMask=0027

NoNewPrivileges=true
PrivateTmp=true
ProtectSystem=full
ProtectHome=true
ProtectKernelTunables=true
ProtectKernelModules=true
ProtectControlGroups=true
ReadWritePaths=/var/lib/khyeast

[Install]
WantedBy=multi-user.target
UNIT

If command -v node returned a different path, change ExecStart.

Start and enable the service

sudo systemctl daemon-reload
sudo systemctl enable --now khyeast
sudo systemctl status khyeast --no-pager
sudo journalctl -u khyeast -n 100 --no-pager

Test directly on the server:

curl -fsS http://127.0.0.1:8787/api/health
ss -ltnp | grep ':8787'

A healthy response resembles:

{"ok":true,"db":"sqlite","imageOptimiser":true}
Sharp fallbackIf imageOptimiser is false, uploads still work and are stored safely, but responsive WebP optimization is unavailable. Review npm ci output, architecture compatibility, and service logs.

Useful service commands

sudo systemctl restart khyeast
sudo systemctl stop khyeast
sudo systemctl start khyeast
sudo systemctl is-active khyeast
sudo journalctl -u khyeast -f
Do not run two managersDo not start the same application with both systemd and PM2, or with both systemd and Passenger. Duplicate processes can fight over the same port and make incidents difficult to diagnose.
Chapter 9

Configure Nginx and HTTPS

Nginx owns public ports 80 and 443. Node remains behind it. Port 80 must redirect to HTTPS before a request reaches Node.

Phase A: temporary HTTP configuration for certificate issuance

sudo tee /etc/nginx/sites-available/khyeast >/dev/null <<'NGINX'
server {
    listen 80;
    listen [::]:80;
    server_name example.com www.example.com;

    client_max_body_size 210m;

    location / {
        proxy_pass http://127.0.0.1:8787;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header X-Forwarded-Port $server_port;
        proxy_connect_timeout 10s;
        proxy_send_timeout 300s;
        proxy_read_timeout 300s;
    }
}
NGINX

sudo ln -sfn /etc/nginx/sites-available/khyeast /etc/nginx/sites-enabled/khyeast
sudo rm -f /etc/nginx/sites-enabled/default
sudo nginx -t
sudo systemctl reload nginx

This temporary HTTP proxy exists only so the ACME challenge can be completed. Production Admin login over HTTP is intentionally refused.

Request the certificate

sudo certbot certonly --nginx \
  -d example.com \
  -d www.example.com

Use a monitored operations email, accept the terms, and do not share the private key. If you use only one hostname, request only that hostname.

Phase B: final HTTPS and redirect configuration

sudo tee /etc/nginx/sites-available/khyeast >/dev/null <<'NGINX'
server {
    listen 80;
    listen [::]:80;
    server_name example.com www.example.com;
    return 308 https://example.com$request_uri;
}

server {
    listen 443 ssl http2;
    listen [::]:443 ssl http2;
    server_name www.example.com;

    ssl_certificate /etc/letsencrypt/live/example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/example.com/privkey.pem;
    include /etc/letsencrypt/options-ssl-nginx.conf;
    ssl_dhparam /etc/letsencrypt/ssl-dhparams.pem;

    return 308 https://example.com$request_uri;
}

server {
    listen 443 ssl http2;
    listen [::]:443 ssl http2;
    server_name example.com;

    ssl_certificate /etc/letsencrypt/live/example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/example.com/privkey.pem;
    include /etc/letsencrypt/options-ssl-nginx.conf;
    ssl_dhparam /etc/letsencrypt/ssl-dhparams.pem;

    client_max_body_size 210m;

    location / {
        proxy_pass http://127.0.0.1:8787;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto https;
        proxy_set_header X-Forwarded-Port 443;

        proxy_connect_timeout 10s;
        proxy_send_timeout 300s;
        proxy_read_timeout 300s;

NGINX

sudo nginx -t
sudo systemctl reload nginx
Certificate pathsCertbot uses a directory named after the certificate's primary name. Confirm with sudo certbot certificates and adjust the paths if your certificate directory differs.

Why the proxy headers are exact

  • Host preserves the real public hostname for canonical and trust checks.
  • X-Forwarded-For carries the visitor chain. Express accepts it only from trusted proxy peers.
  • X-Forwarded-Proto https lets Node issue the production __Host-ky_admin Secure cookie and HSTS.
  • The port-80 virtual host redirects and never proxies. This prevents a real HTTP request from being mistaken for HTTPS if a protocol header is absent.

Check certificate renewal

sudo systemctl status certbot.timer --no-pager
sudo certbot renew --dry-run

Basic public checks

curl -I http://example.com/
curl -I https://example.com/
curl -fsS https://example.com/api/health
curl -I https://example.com/sitemap.xml
curl -I https://example.com/robots.txt

The HTTP request should return 308 to HTTPS. The HTTPS response should include application security headers. Do not add a blanket Nginx cache: live HTML and /api/content intentionally revalidate.

Chapter 10

Verify proxy, cookies, IP, and security

A page loading over HTTPS is not enough. Admin cookies, payment callbacks, rate limits, and audit logs depend on Node detecting the browser-facing protocol and the real visitor IP correctly.

Perform the required real-host Admin test

  1. Open https://example.com/admin by typing it directly in a real browser.
  2. Log in with the production Admin credentials.
  3. Open the Admin tab named «امنیت و محدودیت‌ها» (Security and limits).
  4. Confirm the effective protocol is HTTPS.
  5. Confirm the source is forwarded protocol (or the guarded trusted-proxy fallback on a host that strips the header).
  6. Confirm req.ip is the visitor's real public IP, not 127.0.0.1, the Nginx address, or an attacker-supplied value.
  7. Repeat once from a phone on mobile data to prove different visitors produce different IPs.

Inspect the Admin cookie

In browser DevTools → Application/Storage → Cookies, production Admin authentication should use:

Name__Host-ky_admin
SecureYes
HttpOnlyYes
SameSiteStrict
Path/
Domain attributeAbsent, as required by the __Host- prefix
Never “fix” login by weakening the cookie If production login returns 426 or the cookie is not stored, fix TLS and proxy detection. Do not remove Secure, replace the __Host- cookie, or broadly trust arbitrary Host / forwarding headers.

Trust-proxy rules

  • Same-host Nginx normally works with loopback, linklocal, uniquelocal.
  • Keep port 8787 blocked at both UFW and the cloud firewall.
  • Do not use TRUST_PROXY=true while a client can reach Node directly.
  • For a load balancer or CDN, trust only its known subnet/hop topology and configure the edge's real-IP feature. Test spoofed X-Forwarded-For from outside.
  • All workers must share one stable ADMIN_SECRET; rate-limit counters are already shared through SQLite on one host.

Command-line header checks

curl -sSI https://example.com/ | sed -n '1,25p'
curl -sSI https://example.com/admin | sed -n '1,25p'

# Direct Node access should fail from another machine:
curl --connect-timeout 3 http://SERVER_PUBLIC_IP:8787/api/health

The last command should time out or be refused. Test it from outside the server, not from localhost.

Chapter 11

Configure the application and go live

The infrastructure can be healthy while the business configuration is incomplete. Finish these steps before accepting real orders.

First Admin session

  • Log in only at the final HTTPS hostname.
  • Check the Security tab's effective protocol, real IP, proxy peer, and rate-limit status.
  • Review all rate limits. Disable them only temporarily during controlled troubleshooting.
  • Confirm products, prices, stock, units, active state, and shipping settings.
  • Review Persian content and English/Arabic overrides.
  • Upload a test image and verify responsive variants render.
  • Back up all persistent state before the first unused-file cleanup. Confirm the 24-hour draft grace period and 30-day quarantine; cleanup must return 503—not infer from defaults—if content.json is unavailable.

Configure SMS

  1. Enter sms.ir settings in Admin.
  2. Switch from log-only mode to the intended production transport.
  3. Send OTP to a controlled phone.
  4. Test resend timing and both registered and unregistered flows.
  5. Confirm logs do not expose OTPs to unauthorized operators. Restrict journal access.

Configure ZarinPal

  1. Enter production merchant/payment settings in Admin.
  2. Confirm PUBLIC_ORIGIN is the final HTTPS origin before generating any payment request.
  3. Use a gateway-provided test method or one controlled low-value transaction.
  4. Verify callback success, order status, inventory, authority history, and separate ref_id.
  5. Test a canceled payment and a payment retry.
  6. Review inquiry, reverse, refund, and “needs attention” operations with authorized staff.
CurrencyThe application stores and sends amounts in Iranian rial (IRR). Confirm displayed toman conversions against the rial values entered in Admin.

Chapter 12

Back up and restore correctly

A backup is not complete until it includes content, SQLite, uploads, and the stable environment secret—and until a restore has been tested.

What to back up

ItemLocation in this guideSensitivity
All mutable state/var/lib/khyeast/Personal, commercial, payment and account data
Runtime environment/etc/khyeast/khyeast.envCritical secrets and Admin password
Operational configurationsystemd and Nginx filesInfrastructure details
Code versionGit commit/tagNot secret; record exact release

Safest simple backup: brief controlled stop

SQLite uses WAL. Stopping the service for the archive gives a consistent snapshot of the database, content, and uploads together:

sudo install -d -m 0700 /var/backups/khyeast

sudo systemctl stop khyeast
sudo tar --numeric-owner -C /var/lib -czf \
  /var/backups/khyeast/khyeast-$(date -u +%Y%m%dT%H%M%SZ).tar.gz \
  khyeast
sudo systemctl start khyeast

sudo systemctl is-active khyeast
sudo tar -tzf /var/backups/khyeast/khyeast-*.tar.gz | head

Back up /etc/khyeast/khyeast.env separately into an encrypted secrets vault or encrypted archive. Never place it in an unencrypted general backup bucket.

Automated backup script

sudo tee /usr/local/sbin/backup-khyeast >/dev/null <<'SCRIPT'
#!/usr/bin/env bash

  1. Provision a clean compatible server and install the code version recorded with the backup.
  2. Stop the application.
  3. Move the current data aside—do not immediately delete it.

  6. Correct ownership, start, inspect logs, and perform the full smoke test.

Chapter 13

Deploy updates and roll back

Code is replaceable; production state is not. Back up first, never overwrite persistent data, and remember that database migrations run automatically at startup.

Simple safe update with maintenance downtime

# 1. Confirm current state and create a backup.
sudo /usr/local/sbin/backup-khyeast
cd /srv/khyeast/app
git status --short
git rev-parse HEAD

# 2. Stop before changing node_modules or dist in place.
sudo systemctl stop khyeast

# 3. Fetch an intentional reviewed release.
git fetch --tags origin
git switch main
git pull --ff-only origin main

# 4. Reproduce dependencies, test, and build for the real origin.
npm ci
npm test
PUBLIC_ORIGIN=https://example.com npm run build

# 5. Restore code read permissions and restart.
sudo chown -R "$USER":khyeast /srv/khyeast/app
sudo chmod -R o-rwx /srv/khyeast/app
sudo chmod -R g+rX /srv/khyeast/app
sudo systemctl start khyeast

# 6. Verify.
sudo systemctl status khyeast --no-pager
curl -fsS https://example.com/api/health
git log -1 --oneline
Why stop first?Running npm ci removes and recreates node_modules; building replaces dist. Doing that inside the live process's working tree can produce mixed assets or runtime failures.

Advanced: short-downtime atomic releases

For frequent releases, keep versioned directories such as /srv/khyeast/releases/20261024-180000 and point /srv/khyeast/current at one release. Build and test the next release while the old one runs, atomically switch the symlink, then restart. Persistent data remains in /var/lib/khyeast.

Perform this one-time transition during a maintenance window:

sudo systemctl stop khyeast
sudo install -d -m 0750 -o "$USER" -g khyeast /srv/khyeast/releases
initial="/srv/khyeast/releases/initial-$(date -u +%Y%m%dT%H%M%SZ)"
mv /srv/khyeast/app "$initial"
ln -s "$initial" /srv/khyeast/current
sudo systemctl edit --full khyeast

In the editor, change only the unit's working directory to WorkingDirectory=/srv/khyeast/current. Save, then activate and verify the updated unit:

sudo systemctl daemon-reload
sudo systemctl start khyeast
sudo systemctl status khyeast --no-pager
readlink -f /srv/khyeast/current
Path changes after transitionOnce atomic releases are enabled, use /srv/khyeast/current wherever later operational examples refer to /srv/khyeast/app.

A release switch can then follow this pattern:

set -euo pipefail
release="/srv/khyeast/releases/$(date -u +%Y%m%dT%H%M%SZ)"
previous=$(readlink -f /srv/khyeast/current)
test -n "$previous"
printf 'Previous release: %s\n' "$previous"

git clone https://github.com/m-ali-98/Khyeastwebsite.git "$release"
cd "$release"
git checkout main
npm ci
npm test
PUBLIC_ORIGIN=https://example.com npm run build
sudo chown -R "$USER":khyeast "$release"
sudo chmod -R o-rwx "$release"
sudo chmod -R g+rX "$release"

sudo /usr/local/sbin/backup-khyeast
rm -f /srv/khyeast/current.next
ln -s "$release" /srv/khyeast/current.next
sudo mv -Tf /srv/khyeast/current.next /srv/khyeast/current
sudo systemctl restart khyeast
curl -fsS https://example.com/api/health

Rollback

If startup or smoke tests fail, inspect logs first. For an atomic release, use the previously printed path, switch current back atomically, and restart:

previous=/srv/khyeast/releases/REPLACE-WITH-PREVIOUS-RELEASE
test -d "$previous"
rm -f /srv/khyeast/current.rollback
ln -s "$previous" /srv/khyeast/current.rollback
sudo mv -Tf /srv/khyeast/current.rollback /srv/khyeast/current
sudo systemctl restart khyeast
curl -fsS https://example.com/api/health
Code rollback is not always a data rollbackStartup may already have applied a forward database migration. Do not assume old code is compatible with migrated data. For a migration-related incident, restore the pre-deploy data backup together with the previous code after assessing any orders received since that backup.
Rules for every update Record the old and new commit IDs; verify a pre-deploy backup; use npm ci; build with the production origin; never replace /var/lib/khyeast; smoke-test health, Admin, content, uploads, accounts, and payment configuration; then monitor logs and errors closely.

Log handling

  • Application logs are in journald: journalctl -u khyeast.
  • Nginx access/error logs are under /var/log/nginx and normally rotate through logrotate.
  • Restrict membership of systemd-journal and log access; log-mode SMS can contain OTP test output.
  • Do not log environment files, cookies, bearer tokens, payment credentials, full callback URLs with secrets, or backup contents.
  • Set a retention policy appropriate for security investigations and privacy obligations.

Capacity and SQLite

SQLite is configured with WAL, busy timeout, transactions, and savepoints. It is appropriate for this single-host deployment. Short write transactions still need monitoring under a flood. Use Nginx/CDN/WAF limits as the first line of volumetric defense; application rate limits are not a substitute for edge protection.

  • Keep the database on local SSD.
  • Keep free disk space for WAL, uploads, and temporary image processing.
  • Start with one Node process. Load-test before adding workers.
  • Do not horizontally scale multiple machines around one SQLite file.
  • Use the Admin archive lifecycle instead of deleting financially significant orders.

Chapter 16

cPanel / Apache / Passenger appendix

Use this chapter instead of systemd/Nginx when the Linux host is managed by cPanel's “Setup Node.js App” and Passenger. The same application, state, HTTPS, and proxy rules still apply.

Application setup

  1. Select Node.js 22 or newer and production mode.
  2. Place the repository outside public_html.
  3. Set the application root to the repository and startup file to server/index.js.
  4. Do not manually set PORT unless the host explicitly requires it; Passenger normally injects the listening endpoint.
  5. Add the required environment variables from Chapter 7 through cPanel's environment UI.
  6. Use persistent writable paths for DATA_DIR, DB_FILE, and UPLOAD_DIR. Ensure every Passenger worker sees the same local files.
  7. Run npm ci and PUBLIC_ORIGIN=https://example.com npm run build in cPanel Terminal or SSH.
  8. Restart through cPanel's application control. Use Passenger's restart mechanism only if your host documents it.

Apache proxy contract

  • Prefer X-Forwarded-Proto: https on the HTTPS virtual host.
  • Preserve the public Host.
  • Forward the real client chain in X-Forwarded-For.
  • Port 80 must redirect to HTTPS before Passenger. If port 80 must be proxied, it must explicitly send X-Forwarded-Proto: http; it must never omit the protocol header.
  • Keep the Passenger/internal Node endpoint inaccessible to public clients.
Guarded fallback is not a replacement for a correct proxy If a trusted cPanel/Apache proxy omits X-Forwarded-Proto, production can infer HTTPS only when PUBLIC_ORIGIN is HTTPS, the real Host matches PUBLIC_ORIGIN/TRUSTED_HOSTS, and the socket peer is trusted. A port-80 redirect is still mandatory.

Post-deploy checks

https://example.com/api/health
https://example.com/sitemap.xml
https://example.com/robots.txt
https://example.com/admin

Log in on the real HTTPS host, then inspect the Security tab. The effective protocol must be HTTPS and req.ip must be the visitor—not a Passenger worker. Do not substitute a localhost curl test for this browser check.

Passenger workers and SQLite

Rate-limit counters and reservations are stored in SQLite, so ceilings do not multiply by worker count. SQLite still requires one local persistent data path and short writes. Monitor SQLITE_BUSY and avoid an excessive Passenger worker count. Every worker must receive the same ADMIN_SECRET.

Chapter 17

Static-only deployment limits

A static host can publish dist/ as a limited read-only fallback, but it is not a complete deployment of this product.

What static hosting can provide

  • Built public pages and assets.
  • Generated route HTML, sitemap, robots, canonical metadata, and static 404 behavior where the host honors the generated rules.
  • Only the content present at build time.

What static hosting cannot provide

  • Admin login or content publication.
  • Contact-message storage.
  • Customer accounts, OTP, addresses, or sessions.
  • Cart checkout, live inventory, orders, or comments.
  • ZarinPal payment creation, callback verification, inquiry, reverse, or refund.
  • sms.ir delivery.
  • Uploads or unused-file cleanup.
  • Runtime SEO based on current CMS/database content.
DecisionIf the site will sell products or use Admin, deploy the Node application. Do not point the domain at npm run preview; Vite preview is not the production API server.
